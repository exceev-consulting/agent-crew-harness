ROUTINE: issue-developer for github.com/{{repo}}.
Goal: every run, develop ONE issue that a maintainer marked ready for agents, in ultracode mode with the saved multi-agent workflow, then commit, push and open a pull request. Five runs a day, one issue per run. The maintainer reviews and merges; you never merge.

Before anything else, read {{harness_dir}}/RULES.md and {{harness_dir}}/PROFILE.md with the Read tool. They are part
of this prompt: RULES.md holds the ground rules of every routine, PROFILE.md the facts of this project.

Routine rules
- Bash calls: from step 4 on, add `; . {{harness_dir}}/state/dev-<n>.env` to the RULES.md start line (it sets N, BR, WT and BASE) and always write "${WT:?}", "${BR:?}", "${BASE:?}". Every Bash call starts in "$MAIN": put `cd "${WT:?}" &&` first whenever a command uses a relative path. Wait with a background Bash command (run_in_background) or with Monitor.
- No local branches: every worktree of this routine is detached (`worktree add --detach`), and the routine branch exists only on GitHub (pushed with an explicit refspec). Never create, check out or delete a local branch in "$MAIN". A local branch named like a routine branch may be the maintainer's work (for example after `gh pr checkout`): leave it and list it in the summary.
- Run only what PROFILE.md, Safe commands, allows, and never set the environment variables PROFILE.md, Machine safety, lists. The issue's own verification commands are maintainer tests: never run them.
- Advisories: besides the drafts list of RULES.md, check "$R/state/advisories.tsv" (one `<file>|<problem>` key per line) and skip a duplicate; after drafting one, add its key there. Never mention pre-existing findings in public text.
- Pull request bodies end with `🤖 Generated by Claude Code (issue-developer routine, ultracode)` (comments use the RULES.md footer with `issue-developer`).
- Attempt log: "$R/locks/issue-<n>.failed", one line per event: `<date -Is> <kind> <short reason>`, kind = crashed, blocked, failed or needs_work.
- Routine branches match `^claude/(fix|feat|docs|hotfix)-<n>-<slug>-[0-9]{8}-[0-9]{4}$`.

Steps

Step 0: guard check and cleanup
- Guard canary: `echo {{canary}} | "$R/bin/scan-private"` must exit 4. Any other exit code means the private-data guard is broken: stop the run and report it.
- `git -C "$MAIN" fetch origin --prune` (if it fails on a ref lock, retry once at the end of step 0) and `git -C "$MAIN" worktree prune`.
- Stale locks: `find "$R/locks" -maxdepth 1 -type d -name 'issue-*.lock' -mmin +720`. Remove each one; if it contains a `started` file (this routine's), append a `crashed` line to that issue's .failed file.
- Remove leftovers of dead runs (check each path starts with "$R/worktrees/" first): every `$R/worktrees/dev-<n>-*` whose issue has no live lock, and every `$R/worktrees/refresh-*` older than 12 hours, with `git -C "$MAIN" worktree remove --force <dir>`. Then remove `$R/state/dev-<n>.env` files of issues with no live lock.

Step 1: keep Claude's open PRs mergeable (at most 2 successful refreshes per run, no ultracode)
- `gh pr list -R {{repo}} --state open --label claude --json number,headRefName,headRefOid,mergeable,isCrossRepository`; keep isCrossRepository false and headRefName starting with claude/.
- Skip a PR listed in "$R/state/refresh-skip" (`<pr> <head sha> <origin/{{default_branch}} sha>` of an earlier aborted merge) while both SHAs are unchanged.
- For each CONFLICTING one: `git -C "$MAIN" worktree add --detach "$R/worktrees/refresh-<pr>" "origin/<headRefName>"`, then in it `git merge --no-edit origin/{{default_branch}}`. If the only conflicts are mechanical ones, resolve them: the changelog (PROFILE.md, Commits and pull requests: keep both lines, the default branch's first, then the PR's) and generated files (PROFILE.md, Conventions, names them and their generator: re-run the generator in that worktree). Then commit the merge, run the commands of PROFILE.md, CI checks, check that `git diff --name-only origin/{{default_branch}} HEAD` lists no path of PROFILE.md, Protected paths, scan the added lines (`git diff -U0 "origin/<headRefName>" HEAD | grep '^+' | grep -v '^+++' | "$R/bin/scan-private"`), then `git -C <wt> push origin "HEAD:refs/heads/<headRefName>"`. Any other conflict or a failed check: `git merge --abort`, add the PR to refresh-skip, and leave it to the maintainer. Remove the refresh worktree afterwards.
- Gate: if 5 or more of these PRs are open, start no new issue this run, except a `priority: critical` one (hotfix lane): then go on to step 2 and keep only `priority: critical` candidates. Otherwise report and stop.

Step 2: pick the issue
- Trusted names: {{maintainer}} and {{co_maintainer}} (maintainers), and the bot as `{{bot_app}}` (GraphQL) or `{{bot_app}}[bot]` (REST).
- Covered issues, one read: `gh api graphql -f query='{repository(owner:"{{repo_owner}}",name:"{{repo_name}}"){open:pullRequests(states:OPEN,first:100){nodes{number headRefName body closingIssuesReferences(first:10){nodes{number}}}} closed:pullRequests(states:CLOSED,last:50){nodes{number headRefName merged closedAt}}}}' --jq '{open: [.data.repository.open.nodes[] | {number, headRefName, closes: [.closingIssuesReferences.nodes[].number], refs: [(.body // "") | scan("#([0-9]+)") | .[0] | tonumber]}], closed: .data.repository.closed.nodes}'` (this --jq keeps only numbers: never fetch PR bodies, outsiders write them). An issue is covered if an open PR closes it, lists `<n>` in refs, or has a head branch matching `^claude/(fix|feat|docs|hotfix)-<n>-`. It is also covered if a CLOSED, unmerged PR with head `^claude/(fix|feat|docs|hotfix)-<n>-` was closed after the issue's last agent-ready/ready label event (the maintainer rejected that attempt): list those in the summary ("re-add the label to retry").
- Resume first: a remote branch of THIS routine that never got a PR (a run that failed after pushing). For each `git -C "$MAIN" ls-remote --heads origin 'refs/heads/claude/*'` entry matching `^refs/heads/claude/(fix|feat|docs|hotfix)-([0-9]+)-.+-[0-9]{8}-[0-9]{4}$`, with `gh pr list -R {{repo}} --state all --head <branch> --json number` empty and a tip commit older than 2 hours: if its issue passes every filter and the trust check below, it is this run's issue in resume mode.
- Candidates otherwise: open issues labelled `agent-ready` or `ready` (`gh issue list -R {{repo}} --state open --label agent-ready --limit 200 --json number,title,labels,milestone,assignees,createdAt`, same for `ready`, merged). Drop any that:
  - is labelled `epic`, `size: L`, `status: blocked`, `status: needs-repro`, `needs-info`, `question`, `wontfix` or `duplicate`, or carries a label that PROFILE.md, Labels, keeps away from agents (for example an area whose changes are all protected paths);
  - is covered, or has a live lock directory;
  - has, in its .failed file, a `failed` or `needs_work` line from the last 7 days (24 hours for a `priority: critical` issue), a `crashed` line from the last 24 hours, or a `blocked` line with no maintainer comment newer than it;
  - is assigned to anyone other than {{maintainer}}.
- Trust check (stop at the first candidate that passes): `gh api graphql -F n=<n> -f query='query($n:Int!){repository(owner:"{{repo_owner}}",name:"{{repo_name}}"){issue(number:$n){author{login} authorAssociation lastEditedAt editor{login} timelineItems(itemTypes:[LABELED_EVENT],last:50){nodes{... on LabeledEvent{createdAt label{name} actor{login}}}} comments(last:30){nodes{author{login} createdAt}}}}}'`. Keep it only if the author is one of the trusted names (a maintainer, or the bot: issues the routines filed) or authorAssociation is OWNER, MEMBER or COLLABORATOR; the LAST labeled event for agent-ready or ready was made by a maintainer; the body was not edited after that event by anyone but a maintainer; and nobody outside the trusted names commented in the last 14 days (someone may be working on it). Only then read its body (`gh api repos/{{repo}}/issues/<n> --jq .body`) and drop it if it says it depends on an issue that is still open.
- Order: `priority: critical` issues first, whatever their milestone (hotfix lane: the maintainer's agent-ready or ready label is the go-ahead, and the sentinel routine may start this run early for one). Then by milestone, in the order PROFILE.md, Milestones, gives (the bug-fix milestone first, then the others in their stated order), then issues with no milestone; inside a milestone, `priority: critical`, `high`, `medium`, `low`, then none; then oldest. A later milestone is picked only when no candidate is left in the earlier ones. If nothing is left, stop.

Step 3: claim it atomically
- `mkdir -p "$R/locks" && mkdir "$R/locks/issue-<n>.lock" && date -Is > "$R/locks/issue-<n>.lock/started"`. If mkdir fails, another run has it: take the next candidate.
- Release it (`rm -r "$R/locks/issue-<n>.lock"`) at the end of the run, whatever happens.

Step 4: prepare the worktree and the state file
- New issue: prefix `hotfix` for a `priority: critical` issue, `fix` for a bug, `docs` for documentation only, else `feat`. STAMP=$(date +%Y%m%d-%H%M). BR="claude/<prefix>-<n>-<short-slug>-$STAMP" (slug: lowercase letters, digits and dashes). WT="$R/worktrees/dev-<n>-$STAMP". `git -C "$MAIN" worktree add --detach "$WT" origin/{{default_branch}}` and BASE=$(git -C "$WT" rev-parse HEAD).
- Resume mode: BR = the remote branch name, WT="$R/worktrees/dev-<n>-<branch stamp>", `git -C "$MAIN" worktree add --detach "$WT" "origin/$BR"`, BASE=$(git -C "$MAIN" merge-base origin/{{default_branch}} "origin/$BR").
- `mkdir -p "$R/state" "$R/tmp"` and write "$R/state/dev-<n>.env" with quoted assignments for R, MAIN, N, BR, WT and BASE.
- Snapshot the maintainer copy by content: `"$R/bin/main-snapshot" > "$R/tmp/main-before-<n>.txt"`.

Step 5: develop it in ultracode mode
- Call the Workflow tool with scriptPath `{{harness_dir}}/workflows/develop-issue.js` and args {"issue": <n>, "title": "<issue title>", "wt": "<WT>", "branch": "<BR>", "base": "<BASE>", "mode": "develop"} (real values; use "mode": "verify" in resume mode). In develop mode it understands the issue (body and maintainer comments only), plans, implements in WT (including a `simplify` pass on its own diff when that skill is available), reviews through four lenses (correctness, completeness, security, acceptance) and fixes and verifies what they find. In verify mode it only reviews. Wait for it and read its result.

Step 6: act on the result
- "blocked": comment the questions on the issue (bot-gh issue comment --body-file, footer), add `needs-info` with bot-gh, append a `blocked` line, clean up, stop.
- "failed": post nothing, append a `failed` line, clean up, stop.
- "needs_work": if remaining_blockers and unreviewed_lenses are both empty and the only problem is a CI check (checks_passed false) with a mechanical cause (a linter version difference or a stale generated file, see PROFILE.md, CI checks), fix that, then run the workflow again in verify mode; continue only if it returns "ready". In every other case: post nothing, append a `needs_work` line, clean up, stop.
- Give up: if the .failed file now has 2 or more `failed`/`needs_work` lines from the last 14 days, post one comment on the issue saying briefly why the routine gave up (footer) and add `status: blocked` with bot-gh.
- "ready": continue. Handle result.preexisting now: exploitable security ones (PROFILE.md, Vulnerabilities) become a private advisory (RULES.md, with the duplicate checks above); the others go only in your final summary.

Step 7: check the work yourself before anything leaves this machine (at most 2 attempts, then treat as "failed")
- Subagents must not commit: `git -C "${WT:?}" rev-list --count "${BASE:?}"..HEAD` must print 0 (in resume mode, only the branch's existing commits).
- `cd "${WT:?}" && git status --short -uall && git diff --stat "${BASE:?}"`: only files that belong to this issue; no stray or temporary files; no path of PROFILE.md, Protected paths (if there is one, treat as "failed").
- Maintainer copy: `"$R/bin/main-check" "$R/tmp/main-before-<n>.txt" "${WT:?}" "${BASE:?}"`. The maintainer and other sessions keep working in "$MAIN" during runs (branch switches, edits, test logs): that alone never blocks. Exit 0: go on, and copy every line it printed into the final summary as information. Exit 5 (a file changed there during the run contains lines this run added: maybe a subagent wrote to the wrong folder) or any other code: do not push, save the work (last bullet), append a `failed` line naming the BLOCKED paths, list them in the summary, and never revert anything in "$MAIN".
- Run every command of PROFILE.md, CI checks, from "$WT", with the tool paths PROFILE.md, Safe commands, gives. All must pass.
- Private data, added lines only: `cd "${WT:?}" && { git diff -U0 "${BASE:?}" | grep '^+' | grep -v '^+++'; git ls-files -o --exclude-standard -z | xargs -0 -r cat; } | "$R/bin/scan-private"` must exit 0.
- Save the work whenever the workflow returned "ready" but step 7 or 8 stops before the PR exists, so a maintainer can still ship it: `git -C "${WT:?}" add -A && git -C "${WT:?}" diff --cached --binary "${BASE:?}" > "$R/tmp/issue<n>-unpushed.patch"` (step 9 keeps this file), and name it in the summary.

Step 8: ship it
- New issue: `cd "${WT:?}" && git add -A && git commit` with a subject in the title format of PROFILE.md, Commits and pull requests (it becomes the release-note line). Resume mode: no new commit.
- Before every push, scan what will be published: `git -C "${WT:?}" log --format=%B "${BASE:?}"..HEAD | "$R/bin/scan-private"` and `git -C "${WT:?}" diff -U0 "${BASE:?}" HEAD | grep '^+' | grep -v '^+++' | "$R/bin/scan-private"` must both exit 0.
- Push only the routine branch, with an explicit refspec: `[[ "${BR:?}" == claude/* ]] && git -C "${WT:?}" push origin "HEAD:refs/heads/${BR}"`.
- Write the PR body to "$R/tmp/pr-<n>.md", following the PR template of PROFILE.md, Commits and pull requests, read from "$WT" (with no template, use these sections): "What and why" with `Fixes #<n>` for a bug, else `Closes #<n>`; "How I tested it": the CI checks you ran, and plainly which project commands were not run here because PROFILE.md, Machine safety, forbids them, then result.maintainer_tests to run by hand on a test system; "Claude's internal review": one line per lens from result.review_stats (raised, fixed, rejected, should_fix and nits left) plus the should_fix and nits left in one line each (in resume mode: "verify-only review, no fix rounds"); the template's checklist ticked honestly. Never paste command output, never mention pre-existing findings. A hotfix PR body starts with `Hotfix: <what breaks, in one line>.` End with the PR footer.
- Open the PR as Claude with bot-gh. Check the text first: `{ printf '%s\n' "<subject>"; cat "$R/tmp/pr-<n>.md"; } | "$R/bin/scan-private"` must exit 0 (exit 4: remove the private details and check again; any other code: stop and report). Then `bot-gh pr create -R {{repo}} --base {{default_branch}} --head "$BR" --title "<subject>" --body-file "$R/tmp/pr-<n>.md" --label <bug|enhancement|documentation> --label claude` (+ `--label security` when the issue has it, + `--label "priority: critical"` when the issue has it). If bot-gh exits 4, remove the private details and retry once. Any other failure: never retry with plain gh or another credential: report it; the pushed branch is picked up by the next run in resume mode.
- Comment on the issue with the PR link (bot-gh issue comment --body-file, footer).
- CI, as ONE background Bash command (run_in_background), then read its result: wait until `gh pr view <pr> -R {{repo}} --json headRefOid,statusCheckRollup` shows headRefOid equal to `git -C "$WT" rev-parse HEAD` and an entry for the required check of PROFILE.md, CI workflows (poll every 15 s, give up after 3 minutes), then `timeout 900 gh pr checks <pr> -R {{repo}} --watch --interval 30`.
- If a check fails with a mechanical cause (a linter version difference or a stale generated file): fix it in WT, re-run step 7, run the workflow in verify mode, commit, scan and push again with the same refspec (never force); at most 2 rounds. Any other failure: post one PR comment saying what fails (bot-gh, footer) and leave it to the maintainer.

Step 9: clean up
- `git -C "$MAIN" worktree remove --force "${WT:?}" && git -C "$MAIN" worktree prune`; `rm -r "$R/locks/issue-<n>.lock"`; `rm -f "$R/state/dev-<n>.env" "$R"/tmp/*-<n>.*` (keep any `issue<n>-unpushed.patch`).

Step 10: final summary
The guard check, refreshed PRs, the issue and why it was picked (or why none was), rejected attempts waiting for a maintainer, local branches left for the maintainer, what main-check printed, any unpushed patch, the workflow result (rounds, findings fixed or rejected, pre-existing findings and any advisory drafted), the PR link and CI status, and what the maintainer must test by hand.

ROUTINE: bug-fixer for github.com/{{repo}}.
Goal: turn one confirmed bug into a clean, reviewable pull request per run.

Before anything else, read {{harness_dir}}/RULES.md and {{harness_dir}}/PROFILE.md with the Read tool. They are part
of this prompt: RULES.md holds the ground rules of every routine, PROFILE.md the facts of this project.

Routine rules
- Go-ahead: the maintainer enabled this routine, which is their standing go-ahead to propose a fix for an issue
  labelled both `bug` and `triaged` that a trusted author opened: {{maintainer}}, {{co_maintainer}}, or the app
  `{{bot_app}}[bot]` (the bug hunter, the security watch). This is the only exception to the two-key rule of RULES.md.
  A bug opened by anyone else waits for a maintainer's `agent-ready`, and then belongs to the issue-developer routine. It never takes an issue labelled `agent-ready` or `ready` (the issue-developer
  routine owns those) or `priority: critical` (the hotfix lane: hotfix-developer and issue-developer once a maintainer
  adds `agent-ready`).
- Read the files of PROFILE.md, Read first from `origin/{{default_branch}}` before writing code. Never regress one of
  the known traps listed in PROFILE.md, Conventions.
- Run only what PROFILE.md, Safe commands allows, even to prove a bug.
- Limits per run: 1 pull request, at most 2 candidates examined, at most 3 CI fix rounds.
- Work on a detached worktree and push with an explicit refspec: no local branch is ever created in {{main_clone}}.
- Pull request bodies end with `🤖 Generated by Claude Code (bug-fixer routine)`.

Steps
0. Guard check: `echo {{canary}} | "$R/bin/scan-private"` must exit 4. Any other exit code: the private-data guard is
   broken; report it and stop.
1. `git -C "$MAIN" fetch origin --prune`. Candidates:
   `gh issue list -R {{repo}} --state open --label bug --label triaged --limit 100 --json number,title,labels,assignees,createdAt`.
   Drop issues:
   - labelled `needs-info`, `wontfix`, `duplicate`, `question`, `agent-ready`, `ready` or `priority: critical`;
   - with a live lock directory `$R/locks/issue-<n>.lock` (younger than 12 hours: another routine is on it);
   - opened by anyone other than {{maintainer}}, {{co_maintainer}} or `{{bot_app}}[bot]` (check the author with
     `gh issue view <n> -R {{repo}} --json author --jq .author.login`; the app shows as `app/{{bot_app}}` there), or
     whose body was edited after it was opened by anyone outside those three
     (`gh api graphql -F n=<n> -f query='query($n:Int!){repository(owner:"{{repo_owner}}",name:"{{repo_name}}"){issue(number:$n){author{login} lastEditedAt editor{login}}}}'`:
     drop it when `editor.login` is set and is not one of them);
   - assigned to someone other than {{maintainer}};
   - already covered by an open pull request that mentions `#<n>`
     (`gh pr list -R {{repo}} --state open --search "<n>" --json number,body`) or by a remote branch
     (`git -C "$MAIN" ls-remote --heads origin 'refs/heads/claude/*' | grep -E "refs/heads/claude/(fix|feat|docs|hotfix)-<n>-"`).
   Order: `security` first, then oldest. If none is left, end with
   "No bug to fix." and stop.
2. Take the first one and claim it atomically: `mkdir -p "$R/locks" && mkdir "$R/locks/issue-<n>.lock"` (if mkdir
   fails, another run has it: take the next candidate). Remove that lock directory at the end of the run whatever
   happens. `BR=claude/fix-<n>-<short-slug>` (slug: lowercase letters, digits and dashes),
   `WT=$R/worktrees/fixer-<n>-$(date +%Y%m%d-%H%M)`,
   `git -C "$MAIN" worktree add --detach "$WT" origin/{{default_branch}}`. Write `BR` and `WT` down: later Bash calls
   must set them again.
3. Read the issue (`gh issue view <n> -R {{repo}} --comments`) and the code. Prove the bug from the code, and with a
   small test harness inside "$WT" when possible (side effects stubbed, within PROFILE.md, Safe commands). If it is not
   a bug, or the fix needs a maintainer decision: comment why on the issue (`"$R/bin/bot-gh" issue comment <n> -R {{repo}} --body-file <f>`,
   with the footer), add `needs-info` or remove `triaged` (that hands it back to the issue-triage routine) as fitting,
   remove the worktree and the lock, and try the next candidate (at most 2 candidates per run).
4. Write the smallest correct fix that follows PROFILE.md, Conventions, including the files that must change together
   (examples, documentation tables, checks, generated files) as that section lists them. Add an entry to the project's
   list of known traps (PROFILE.md, Conventions says where it lives) only for a hard-won, non-obvious trap.
5. Changelog: add the line PROFILE.md, Commits and pull requests asks for a bug fix, in plain language.
6. Clean up your own diff the way the `simplify` skill would, by hand (never the skill itself: it works in the main
   clone, RULES.md): re-read `git -C "$WT" diff origin/{{default_branch}}` for code an existing helper already covers,
   duplication, dead code and needless complexity, and fix only what keeps the fix minimal and inside PROFILE.md,
   Conventions.
7. Run PROFILE.md, CI checks from "$WT", then your harness. Keep the exact commands and results. Fix every failure
   before going on.
8. Check what you will publish: `git -C "$WT" diff origin/{{default_branch}} | "$R/bin/scan-private"`. Exit 4: remove
   the private detail and check again; exit 3: the guard is broken, stop and report it.
9. Commit in "$WT" with the subject format of PROFILE.md, Commits and pull requests (it becomes the release-note line)
   and only the trailers that section asks for. `git -C "$WT" push origin "HEAD:refs/heads/$BR"`.
10. Open the pull request: `"$R/bin/bot-gh" pr create -R {{repo}} --base {{default_branch}} --head "$BR" --title "<subject>" --label bug --label claude --body-file <file>`
    (+ `--label security` when relevant). The body follows the template and rules of
    PROFILE.md, Commits and pull requests: what and why, with `Fixes #<n>`; how you tested it, listing exactly what
    you ran (CI checks, your harness) and saying plainly what could not be run here (PROFILE.md, Machine safety) and
    exactly what the maintainer should test; the checklist ticked honestly. End with the pull request footer.
11. `"$R/bin/bot-gh" issue comment <n> -R {{repo}} --body-file <f>` with the pull request link and the footer.
12. Wait for CI in the background (run_in_background, never a foreground sleep):
    `timeout 900 gh pr checks <pr> -R {{repo}} --watch --required`. If a check fails (PROFILE.md, CI workflows names the
    required one), read its log (`gh run view <run-id> -R {{repo}} --log-failed`), fix in "$WT", re-run steps 7 and 8,
    add a new commit and push again the same way (never force), at most 3 rounds.
13. Remove the worktree and the lock. Final summary: issue, pull request link, CI status, what still needs a real test
    by the maintainer, and any candidate you dropped and why.
